# Fixed-wait audit (set 31 follow-up, branch `inner-agent-speed`)

Every wait in the agent and replay paths outside `src/agent/tools.ts` (agent A's file), with what it
was, what it is now, and why the replacement cannot be slower or unbounded.

| Location | Old wait | New behaviour | Why safe |
| --- | --- | --- | --- |
| `src/daemon/settle.ts` `settleDom` | (already condition-based) | unchanged: MutationObserver, 60ms probe / 250ms quiet / 2s ceiling | kept as the shared primitive; every replacement below reuses it |
| `src/daemon/settle.ts` `settlePage` (new) | — | `settleDom` + wait for the page's own non-streaming fetch/XHR started within 300ms of the settle to finish; event-driven (`requestfinished`/`requestfailed`/`framenavigated` wake it), total ceiling 2s (`maxMs`) | returns at `settleDom` speed (~60ms) when nothing is in flight; websocket/eventsource/non-fetch resources and long-poll-shaped paths (`/longpoll`, `/poll`, `/stream`, `/sse`, `/subscribe`, `/events`, `/notifications`, `/watch`) are never waited on, so Odoo-style forever-polls cost nothing; a navigation clears the pending set so stale entries cannot hold the next settle |
| `src/daemon/refs.ts` `waitForContent` | poll `page.evaluate` every **150ms** up to 5s | one in-page check, then a `MutationObserver` that resolves the instant the first actionable element/text appears, bounded by the remaining deadline | the check runs first, so a ready page returns in one round-trip (was up to one poll interval late); the in-page timer bounds it at the same 5s deadline; an `evaluate` that throws (navigation mid-wait) backs off 50ms on a plain timer and re-checks against the new document instead of returning "ready" as before — strictly more correct, still deadline-bounded |
| `src/daemon/server.ts` ~1616 `dismissBlockingDialogs` | `waitForTimeout(250)` after each Escape | `blockers.first().waitFor({state:'hidden', timeout: DIALOG_CLOSE_MS=250})` | the condition IS "the modal went"; a dialog that closes in 20ms costs 20ms, one that will not close costs the same 250ms as before, then the next of the 3 attempts |
| `src/daemon/server.ts` ~1638 `captureUrlOutputs` | poll `page.url()` every **250ms** up to 5s | `page.waitForURL(predicate)` in a loop, per-iteration budget `URL_OUTPUT_POLL_MS=500` as a backstop | the predicate is evaluated immediately by `waitForURL`, so an already-correct url returns at once and a route that lands in 30ms is seen in 30ms; the 500ms iteration budget only exists for a url an SPA rewrites without a history entry (no navigation event to wake us), and the outer 5s deadline is unchanged |
| `src/daemon/server.ts` ~1598 `shutdown` | `setTimeout(150)` before `process.exit(0)` | **left fixed** (comment added) | what is awaited is the OS draining this process's stdout pipe before `process.exit` truncates it; node exposes no completion signal for that, so there is no condition to check |
| `src/skills/components.ts` ~348 recipe `settle` step | `waitForTimeout(s.ms ?? 300)` (recipes use 200–400ms) | `settleDom(page)` | the recipe's `ms` was an estimate of an editor's re-render, and the re-render is observable; the action before it has already passed Playwright actionability, so the mutation lands inside the 60ms probe; a component that keeps re-rendering is now followed to its real end (up to 2s) instead of being cut off at the guess, and a quiet one costs ~60ms instead of 200–400ms |
| `src/daemon/browser.ts` ~150 new-tab error watch | `setTimeout(250)` per poll, 15s of iterations | `page.waitForEvent('framenavigated', {timeout: ≤250})`, loop bounded by a real 15s deadline | the tab committing a url is the condition; a tab that resolves in 20ms is judged in 20ms; the 250ms cap is a backstop for a url committed without a main-frame navigation event, and the loop is now bounded by wall clock (the old `waited += 250` counted iterations, not time) |
| `src/skills/replay.ts` ~631 loop-shrink | `waitForTimeout(100)` × up to 10 while re-counting | `makeLocator(...).nth(remaining-1).waitFor({state:'detached', timeout: LOOP_SHRINK_WAIT_MS=1000})`, then one recount | "count < remaining" is exactly "the remaining-th match left the DOM"; the recount still uses the same candidate as before, so the edit-in-place vs consumed decision is unchanged; a row already gone resolves instantly, a row that never goes costs the same 1s window as before |
| `src/skills/replay.ts` ~730 `expectedUrl` gate | `setTimeout(100)` × up to `resolveWaitMs()` (3s) while re-reading `page.url()` | `page.waitForURL(predicate)` loop, per-iteration budget `URL_SETTLE_POLL_MS=500`, same 3s deadline | the url is checked before the wait (unchanged fast path: a matching url returns `null` immediately), then the pending navigation wakes us the moment it lands; the 500ms budget is the backstop for a history-less url rewrite; `SITELOOPER_RESOLVE_WAIT_MS` still bounds the whole thing |
| `src/skills/replay.ts` ~1128 locator-chain resolve (`RESOLVE_POLL_MS`) | poll every 100ms up to `resolveWaitMs()` | **left a poll** (comment added) | there is no single DOM condition: each poll re-walks the WHOLE candidate chain so the preference order (and the positional-guess hold) is re-read as a unit. Waiting on any one rung would let a worse candidate win. It runs only after the page has already failed to answer, never on the fast path |
| `src/skills/replay.ts` `sweepPage`'s trailing settle | already `settleDom` | unchanged | — |
| `src/agent/tools.ts` `stateDiff` / `settledSignature` (`SETTLE_MS=150`) | `waitForTimeout(150)` ×2 per action | handed to agent A: replace with `settleDom(page)`, delete `SETTLE_MS` | not this agent's file; the one-line hand-off is in the contract |

## Notes

- `settlePage` is exported and tested but not yet wired into a call site: the only per-action settle
  left in the tree is in `tools.ts`, which agent A owns and which the contract hands `settleDom` (not
  `settlePage`). Wiring it there is a one-word change (`settleDom` → `settlePage`) whenever an
  action's answer, not just its repaint, needs to be in the signature.
- The request tracker in `settle.ts` deliberately duplicates rather than reuses `browser.ts`'s
  `inFlightRequests`: that counter is a bare count of *all* requests (long-polls included) with no
  start time, so it can neither ignore a stream nor answer "started within the last 300ms". Both are
  installed idempotently per page and cost one listener each.
