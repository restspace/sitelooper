# Shared execution

Sitelooper executes a stored procedure two ways:

- **daemon replay** — `src/skills/replay.ts`, driving a live session;
- **the compiled artifact** — a standalone `.flow.ts` generated by
  `src/spec/emit.ts`, run by plain Playwright with no daemon, no repository, no
  model and no Sitelooper runtime.

They are required to reach the same verdict about the same page. Historically
each rule was written twice — once per runner — and the pair agreed only until
one of them was fixed. Three defects in a row had that exact shape, which is what
`PARITY_GAPS.md` and `test/execution-parity.test.ts` exist to catch.

`src/execution/` is the answer to the cause rather than the symptom: ordinary,
type-checked TypeScript that the daemon **imports** and the artifact **embeds**.
One implementation, two callers.

> This branch does not claim full parity. What is shared is listed below; what
> is still target-specific is listed below that, with reasons. `PARITY_GAPS.md`
> is the live audit.

---

## What is shared, module by module

Every module under `src/execution/` is self-contained: it may import Playwright
*types* and *sibling shared modules*, and nothing else. That constraint is
enforced at compile time by `src/spec/runtime-source.ts` and re-checked by
`test/execution-source.test.ts`.

### `text.ts` — the text rules

`WILDCARD`, `IDENTITY_EDGE`, `maskVolatile`, `identitySource`, `identityRe`,
`escapeRe`, `clip`. `src/shared/text.ts` is now `export * from
'../execution/text.js'`, so no daemon call site changed. The artifact embeds the
module instead of carrying a hand-written second copy of the identity boundary
rule.

### `url.ts` — the url rules

`urlShapeOf`, `urlDiff`, `urlMatches`, `softUrlMatch`, `urlParts`, `urlPart`,
`fillParams`, `fillParamsDeep`, `safeDecode`, `originOf`. `src/skills/compile.ts`
re-exports most of them (`compile.ts:8`, `:28`); `originOf` moved here from
`src/skills/store.ts`, which re-exports it, because both runners derive a step's
`stayOnOrigin` from it (the recorded pattern's origin, else the live page's).

This replaced three emitted re-implementations — `urlPart`, `hashState`,
`hashMatch` — that disagreed with the daemon about percent-decoding, trailing
slashes, an unbound `{{dN}}`, duplicate hash keys, and had no notion of the soft
match at all. The artifact now emits one form for every pattern shape.

### `gates.ts` — the step and segment verdicts

| Verdict | Daemon call site | Artifact call site |
|---|---|---|
| `errorPageVerdict` | `errorPage` gate, `replay.ts:866` | emitted `errorPageGate` helper |
| `urlEffectVerdict` | `expectedUrl` gate, `replay.ts:793` | emitted `urlEffect` helper |
| `alertVerdict` | `alerts` gate, `replay.ts:820` | emitted `alertGate` helper |
| `preconditionVerdict` | `replay.ts:249` | emitted `preconditionGate` helper, per segment |
| `markersBound` | `goalSatisfied`, `replay.ts:1369` | emitted `satisfiedGuard` prefix |

Each is a pure function over observations the caller supplies. What differs per
runner is only **how it waits and observes**, never what it decides. The
emitted `verify` phase runs them in replay's own order: error page, url, alerts,
then content expectations. The alerts observation is taken in the lifecycle's
`settle` phase, so the artifact looks at the page at the same moment the daemon's
executor captures its diff.

Where a runner genuinely cannot make an observation, the verdict's TYPE says so
rather than the caller passing a lie. `FingerprintSimilarity` is
`number | null | 'unmeasured'`: a number is the cosine both runners measure
(`fingerprint.ts`, below); `null` means no fingerprint was recorded, or the live
page could not be read, and the url alone decides; `'unmeasured'` means one was
recorded and this caller cannot measure it, and a soft url match is then
refused. Only a `.flow.ts` compiled before the vector travelled in the spec
passes `'unmeasured'` now (see `fingerprint.ts`).

### `fingerprint.ts` — the structural page fingerprint

`fingerprintPage`, `cosine`, `normaliseFingerprint`, `fingerprintPathsInPage`
(the page function, closure-free), `FINGERPRINT_DIMS`,
`FINGERPRINT_CAPTURE_TIMEOUT_MS`. Moved from `src/daemon/fingerprint.ts`, which
re-exports it, so the recorder (`src/agent/loop.ts`, `src/agent/tools.ts`) and
replay did not change.

| | Daemon (`src/skills/replay.ts`) | Artifact (`src/spec/emit.ts`) |
|---|---|---|
| The recorded vector | `skill.preconditions.fingerprint` | `SpecSegment.preconditions.fingerprint`, read back out of `FLOW` by the emitted `recordedFingerprint(stepId, segmentId)` |
| The url | `const startUrl = page.url()` (`:235`), BEFORE the measurement | `page.url()` as the gate's second argument, evaluated ahead of the `cosine(…)` argument, so also before the measurement |
| The measurement | `cosine(skill.preconditions.fingerprint, (await fingerprintPage(page)) ?? undefined)` (`:243`) | the same expression at the `preconditionGate` call site (`emitSegment`) |
| The verdict | `preconditionVerdict(…, startUrl, …, res.similarity)` (`:249`) | `preconditionGate(pattern, url, p, where, similarity)` → `preconditionVerdict` |

The url is read before measuring on both sides: the measurement can take up to
`FINGERPRINT_CAPTURE_TIMEOUT_MS`, and a navigation in flight during it would
otherwise let the artifact judge the landed url while replay judges the one the
segment started on. `spec-emit.test.ts` pins the order in the emitted text and
runs the call against a page whose url moves during `fingerprintPage`.

`cosine` is `null` when either vector holds a non-finite (or non-number) entry,
the same rule `flowToSpec` applies when it omits such a stored vector — so a
hand-edited store gives both runners `null`, not a number to the daemon only.

A vector is 512 numbers, L2-normalised and rounded to three decimals at
capture; `cosine` rounds its result to three decimals. The IR carries the stored
vector verbatim, so the artifact computes the daemon's number to the last digit
and no second rounding exists that could move a similarity across
`SOFT_MATCH_MIN_SIMILARITY`. Its JSON is at most ~3KB (every entry `0.xyz,` or
shorter) and in practice mostly `0,`; the emitter writes it on ONE line of the
`FLOW` literal (`flowLiteral`) rather than 512. A page that could not be read is
`null` on both sides, so the url alone decides — replay's rule, unchanged.

`flowToSpec` copies a vector of exactly `FINGERPRINT_DIMS` numbers; any other
length is one replay can never compare (`cosine` of unequal lengths is `null`),
and leaving it out gives the artifact that same `null`. `lift` refuses a present
vector that is not 512 finite numbers with a `LiftError` naming
`preconditions.fingerprint`. `lower` puts the vector back into the staged skill,
so a repair's replay soft-matches as the artifact does. `repair` and `rerecord`
call `carryFingerprints` (`src/spec/ir.ts`) beside `carryRecipeSnapshot`: the
file's vector is kept unless the skill the verification run used recorded a
different one, which is adopted with a `fingerprint: …` change line. The
file's vector is carried only at the SAME start url pattern; when repair has
widened the pattern it is dropped (it describes another page) and the segment
gets the `fingerprinted` flag instead, with a change line saying why and the
`unmeasured-precondition` warning. A rebuilt segment is matched to the file's
by segment id; by position only when it replaced its counterpart in place
(`matchPriorSegment`: same step, same segment count, same template, the new id
absent from the file and the file's id absent from the rebuild). Segments of
one chain share a template, so an inserted or removed segment matches nothing
positionally, and the rebuilt segment keeps only what its skill recorded.

Back-compat: a file compiled earlier carries only `preconditions.fingerprinted:
true`. It still lifts; the emitter passes `'unmeasured'` for such a segment
(refusing a soft match, the stricter direction) with an
`unmeasured-precondition` warning that says to recompile, and repair/rerecord
keep the flag (with the same diagnostic), at any start pattern, rather than
silently loosening the gate.
The module is embedded only when some segment carries a vector.

Verdict messages describe a live url through `describeUrl` —
`serializeShape(urlShapeOf(url))` — because those messages travel into recovery
prompts and persisted run records, and a query string is where `?token=…` lives.
(A state-shaped hash is still re-serialised; see `PARITY_GAPS.md`.)

### `observe.ts` — live-region alerts

`liveAlerts(page)`, and nothing else: it is the alerts half of the ONE page
capture (`capturePage`, below). It used to restate the selector and the caps,
with a test keeping the two copies in step; now they agree by construction. An
alert the daemon would diff is one the artifact sees. Returns `null` when the
page cannot be read — *unobserved*, never "no alert".

### `snapshot.ts` — the page dialect

`describeInPage` (the in-page capture; `src/daemon/diff.ts` imports it),
`isInteractiveLine`, `capturePage`, `capturePageLines`, `addedLines`,
`lineShows`, `presentOnPage`, `scopeCheckInPage`, `sweepPage`, plus
`SNAPSHOT_LIMITS`, `CAPTURE_TIMEOUT_MS` and `MAX_ADDED_LINES`.

`capturePage` is the single capture — one `page.evaluate` under one timeout race,
returning lines and alerts; `capturePageLines` is its interactive-lines view and
`liveAlerts` its alerts view.

This is what lets the artifact judge the **same lines** the daemon judges — and
ask the same identity question. The artifact's identity gate calls
`presentOnPage` directly, and its `satisfied` helper runs `capturePageLines` +
`lineShows` and then `page.evaluate(scopeCheckInPage, …)`. The emitted `present`
and `sharesScope` helpers that used to restate both are deleted.

The artifact takes its own before/after capture in the step lifecycle and diffs
it with the recorder's own rule, so both runners hand their verdict a real diff
plus a live-page fallback.

### `expect.ts` — the content-expectation verdict

`expectedChangesVerdict`, `namesDialogControl`, `consequentialExpectations`,
`isEchoLine`, `liveLines`, `maskMinted`, `TRANSIENT_LINE`, `SLOT_LINE`,
`DIALOG_LINE`. Daemon: the `expectedChanges` gate, `replay.ts:843`. Artifact: the
emitted `expectChanges` helper. `src/skills/compile.ts:1069` re-exports
`TRANSIENT_LINE` and `maskMinted` for compile-time use.

The emitter no longer rebuilds recorded lines as Playwright locators. That
translation is what dropped unnameable lines silently, and what made
`- combobox "Project": {{v1}}` pass on any visible Project combobox whatever it
showed: the locator only ever matched the name.

### `browser.ts` — the actions

`robustClick`, `fireWhenAttached`, `reactSafeFill`, `reactSafeSelect`,
`syntheticHover`, `settleDom`. Daemon: `src/agent/tools.ts:4`,
`src/daemon/inputs.ts:2`, `src/daemon/settle.ts:2`. Artifact: the emitted
`click`/`hover`/`settle` adapters, and the native half of the recipe ladders
(below) that `fill`/`type`/`select` climb.

### `echo.ts` — reads that only echo what the procedure set

`MIN_ECHO_LEN`, `setsSomething`, `echoKey`, `noteInteraction`,
`candidateNames`, `echoVerdict`. A read whose value is only what the
procedure itself typed, selected or named confirms the control, not that the
app persisted it (grafana's time picker). One ledger per segment in both
runners.

| | Daemon (`src/skills/replay.ts`) | Artifact (`src/spec/emit.ts`) |
|---|---|---|
| The ledger | `interacted`, one per `replaySkill` call | `const typedN = new Set<string>()`, one per emitted segment, declared only when a line uses it |
| Fed by | `noteInteraction` over `args.value`/`args.text` of a `setsSomething` step, and over `candidateNames(chain)` of each target that resolved | the same two calls, emitted ahead of the step's absent-dialog skip (values) and right after its `pick` (names) |
| Asked at | each read: `echoVerdict(interacted, label, value, 'step N')` → `echoedValues` + warning | the emitted `echoRead` after each published read → `run.echoed` (output keys) + `[sitelooper warn]` |
| Consequence | the flow runner drops the label from its confident values; the value still reaches later steps | the value is still published; `run.echoed` says which outputs are not proof of persistence |

### `recover.ts` — the two recovery rungs

`mayNavigateToDestination`, `navigateToDestination`, `linkToDestination`,
`textHeldElsewhere`, `RecoveryHooks`, `HELD_TEXT_READ_MS`. Imports `browser.ts`
(`settleDom`) and `url.ts`.

| | Daemon (`src/skills/replay.ts`) | Artifact (`src/spec/emit.ts`) |
|---|---|---|
| Navigation by recorded destination | `runOneStep`, after a missed resolution: `mayNavigateToDestination(tool, pattern, url, params, inLoopBody)`, then `navigateToDestination` with hooks over `opts.exec('click'/'goto')`; arrival returns `ran` before the gates | a navigation click with a recorded destination (not in a loop body) resolves through the emitted `pickOrNavigate`, hooks over the `click` adapter and `page.goto` (load, 30s); arrival logs `[sitelooper drift]` and returns `skipped`, before the gates |
| Text held elsewhere | the wait's `catch`: `textHeldElsewhere(heldObservations(page, chain), state, text)` | a text wait hoists its observations; the wait's `catch` calls the emitted `textHeldOrThrow`, which drifts and continues or rethrows |

Record ids minted in a loop body: the daemon's `res.created` and the
artifact's `run.created` both accumulate every distinct `changedCreation`
value, in order; the artifact's `<step>.minted` output stays the latest.

### `recipes.ts` — the component recipe runner

`RECIPE_FAMILIES`, `SEED_RECIPES`, `recognizeComponent`, `executeRecipe`,
`verifyRecipe`, `readComponentValue`, `squashText`, `applyRecipe`,
`describeRecipeAttempt`, `snapshotBook`, and the three ladders
`fillWithRecipe`, `typeWithRecipe`, `selectWithRecipe`, plus the `RecipeBook`
and `RecipeSnapshot` types. Imports `browser.ts` for `settleDom` and the
native primitives.

| | Daemon (`src/agent/tools.ts`) | Artifact (`src/spec/emit.ts`) |
|---|---|---|
| `fill` | `fillWithRecipe(page, t(), value, storeBook(new ComponentStore(), page))` (`:1004`) | emitted `fill` adapter: `fillWithRecipe(loc.page(), loc, value, recipeBook)` and nothing ahead of it — recognition first, as in the daemon; the native half's `reactSafeFill` does its own visible-wait and scroll |
| `type` | `typeWithRecipe(…, { timeout, delay: delay_ms ?? 20 })` (`:1008`) | emitted `type` adapter: `typeWithRecipe(…, { timeout: TYPE_TIMEOUT_MS, delay: opts.delay ?? TYPE_DELAY_MS })` — the tool layer's 10s and 20ms |
| `select` | `selectWithRecipe(…, fallbackValue)` (`:1026`) | emitted `select` adapter: `selectWithRecipe(loc.page(), loc, label, recipeBook, fallbackValue)` |
| The book | `storeBook` (`src/skills/components.ts`): `offers`/`choose` over `pickRecipe` on a fresh read of the store, `onAttempt` → `recordOutcome` | `snapshotBook(RECIPES)`, where `RECIPES` is `SpecFlow.recipes` rendered as a JSON literal; no `onAttempt` |
| The result | the tool result string (`describeRecipeAttempt`) | a `[sitelooper recipe] …` log line in the same words |

Recognition order, the click/blur/verify order, `settleDom` for every
`settle`, the NBSP squash, verified-or-nothing and the `offers` gate ahead of
recognition are all decided in the module; each runner adds its book and its
presentation only. The emitter restates no family root and no step list: the
recognition set and the seed procedures travel inside the embedded module, and
the `RECIPES` constant carries only the chosen procedure per (family, intent).

Recognition resolves the target once and PINS the component root as an
`ElementHandle` (the nearest `closest()` hit of the first matching family);
every click, blur and the verification read of that run act on that handle,
and `applyRecipe` disposes it on every exit path. A root re-derived from the
target on each step would change under the recipe's own edits: a text- or
placeholder-located target on an editor stops matching once its content is
replaced, and a selector that also matches a mirrored preview afterwards
would verify against the wrong component. Step targets are looked up inside
the pinned root (`root.$(target)`). A `blur` step with no target blurs the
root itself; a `blur` target the widget does not have is skipped; a missing
`click`/`fill` target throws, so the attempt is unverified. A book whose
`onAttempt` throws (a store write refused by the OS) does not change the
outcome: a verified attempt stays verified and carries a `warning`, which
the daemon's result string appends.

The snapshot is COMPILE-TIME state. `flowToSpec` takes the `ComponentStore`
the compile CLI hands it (the one the daemon reads:
`$SITELOOPER_COMPONENTS_FILE`, else `<home>/components.json`) and calls
`snapshotRecipes` on its list: validated first, then track record, learned
ahead of seed on a tie, demoted omitted — `pickRecipe`'s own rule. Only a flow
with a `fill`, `type` or `select` step somewhere (loop bodies included) is
snapshotted or diagnosed; any other flow carries no `recipes`. A spec
compiled without a store (a test's hand-built flow, a spec repair reloads from
its staged store) carries no `recipes`, and the emitter embeds the shipped seeds,
which is what a fresh install's store holds too. `lift` validates a present
`FLOW.recipes` (version, and each procedure's id/family/intent/steps) and
refuses a malformed one with a `LiftError` naming the field.

`repair` and `rerecord` verify through the daemon, whose recipes are this
machine's store as it stands at that moment (a rerecord may even learn a
variant during its run), so the file they write carries THAT snapshot
(`carryRecipeSnapshot` in `src/spec/ir.ts`): an identical one keeps the file's
own snapshot and FLOW bytes; a different one is adopted with one
`recipes: <family>/<intent> <old> -> <new>` (or `added`/`removed`) change line
beside the other changes, plus the store's `recipe-snapshot` findings. A file
with no snapshot at all predates snapshots; it gets one, a change line, and a
`recipe-snapshot` warning that its artifact ran the shipped seeds and that
`type` and `select` now go through recipes (a recorded `type` into a
contenteditable replaces rather than appends); recompile it and review.

What the store holds that a snapshot cannot express is diagnosed at compile
time as `recipe-snapshot` (a warning, never a blocker — the artifact runs the
same ladder, it only stops learning): a demoted recipe (omitted, and the
artifact never revives it), a (family, intent) left with nothing usable (both
runners go native there, the artifact for good), and a chosen recipe that is
learned rather than a seed (knowledge from this machine's store, travelling as
data). See "What is still target-specific" for the half that stays daemon-only.

This deleted the emitter's own transcription of the fill ladder —
`editorSetValue`, its hardcoded `EDITORS` family table with xpath `up` walks,
the inline `squash`, `EDITOR_SETTLE_MS`/`EDITOR_BLUR_SETTLE_MS` and two
`page.waitForTimeout`s, `FILL_FOCUS_MS` — and gave `type` and `select` a recipe
path they never had in the artifact: an `aria-combobox` the daemon drives by
recipe, or an editor the recording typed into, used to fail there loudly.

### `lifecycle.ts` — the step sequence and the action classes

`runStepLifecycle` enforces `prepare -> act -> settle -> bind -> verify`. A
skipped or stopped action bypasses postconditions without claiming completion;
there is deliberately no catch or retry inside it, so a verification failure can
never be mistaken for failed dispatch. Daemon: `replay.ts:466`. Artifact:
`emit.ts:1322` for every non-loop step — page-level actions such as `back` and
`goto` return from action emission only, never past the lifecycle.

Also `isReadAction`, `isMutatingAction`, `mutatesSteps` (imported by
`compile.ts`, `learn.ts`, `flow.ts` instead of three identical lists), and
`changedCreation`, which is why a rejected click cannot report a creation in
either runner.

### `loop.ts` — the folded-loop policy

`runFoldedLoop` and `LOOP_SHRINK_WAIT_MS`. Daemon: `replay.ts:635`. Artifact:
`emit.ts:1757`. Five rules
that used to be written twice and agreed on three: settle before every count;
first matching candidate, not a `.or()` union, and recount with that same
candidate; the cursor; the progress guard; and the cap as a budget rather than a
finish line. The artifact supplies three observations — settle, resolve the
guard, run the body for one cursor — and the policy does the rest.

The progress guard needs a signature that can actually repeat. The artifact
builds one from what its targets RESOLVED to: `pick` takes a `resolved` sink and
records the winning candidate (plus the cursor, when the shared policy narrowed
an ambiguous candidate to it — `Resolution.nth`), which is what replay's
`resolveChain` returns as `{ …candidate, nth }`. A signature synthesised from
compile-time text alone could never repeat, so the guard could never fire.

The loop GUARD is the chain through `resolveCandidates` with
`{ allowMultiple: true }` and no wait — replay's own guard call — in both.

Constants both runners share — `LOOP_SHRINK_WAIT_MS`, `SLOT_LINE`, the snapshot
limits, `RESOLVE_WAIT_MS`/`RESOLVE_POLL_MS` — live in the shared module and are
referenced from the artifact, not restated in the emitter.

### `point.ts` — geometry as a locator kind

`PointGeometry`, `POINT_MARK`, `pointToken`, `pointLocator`, `markPoint`. A
`point` candidate is resolved in two moves: `markPoint` finds the element under
the recorded point, walks up to the recorded KIND of thing and tags it;
`pointLocator` names the tag. Daemon: through `resolveCandidates` (below).
Artifact: the emitter renders a point candidate as
`{ locator: pointLocator(page, { x, y }), …, point: { x, y, w, h, role, tag, vw, vh } }`
(`src/spec/locators.ts` `observationSource`), so a position-only chain is no
longer refused — the `unsupported-capability` diagnostic for it is retired. The
box is also the plausibility yardstick for every positional guess in the chain.

### `resolve.ts` — the locator-resolution policy

`resolveCandidates`, `CandidateObservation`, `ResolvePolicy`, `Resolution`,
`MissReason`, `structuralCandidate`, `candidateRank`, `orderCandidates`,
`identityFields`, `identityValues`, `RESOLVE_WAIT_MS`, `RESOLVE_POLL_MS`.

| | Daemon (`src/skills/replay.ts`) | Artifact (`src/spec/emit.ts`) |
|---|---|---|
| Call | `resolveChain` (`:957`) | emitted `resolveTarget` / `pick` / `readOptional`; loop guard calls `resolveCandidates` directly |
| Observations | built live per stored candidate: `makeLocator`, index, `structural`, kind, filled JSON, `nth`, geometry, `retired` | rendered at compile time by `observationSource` (`locators.ts`): the same fields as literals, `pointLocator` for a point, `retired` omitted |
| `requireIdentity` | `identityOfPrimary` (`:1021`) — `identityValues` over the whole chain's fields with the skill's known slots | `identitySource` renders the same call: `identityValues({ v1: p.v1 }, ['Mark {{v1}}'])` over the segment's known slots |
| `stayOnOrigin` | `originOf(urlPattern) ?? originOf(page.url())` | `'http://…'` when the pattern's origin is concrete, else `originOf(page.url()) ?? undefined` |
| `allowMultiple` / `ambiguousNth` / `waitMs` | `read_all` or an absence wait / the loop cursor / `RESOLVE_WAIT_MS`, 0 for an absence wait | the same, rendered by `policySource` |

The policy decides everything: class order, the point mark, the identity guard,
plausibility, the origin guard, ambiguity and cursor narrowing, the structural
hold, the whole-chain wait, and the reasons a candidate was passed over. Each
runner adds presentation only — the daemon its telemetry and evidence, the
artifact its `[sitelooper drift]` line (now naming the rejected candidates in
the shared `MissReason` words), the loop sink and the throw. EVERY locator step
of the artifact goes through it, single-candidate too: Playwright's strict mode
is not the daemon's rule. The static `.filter({ hasText })` guards and the
`specOf` pre-ordering that used to stand in for the policy in `locators.ts` are
deleted; the chain travels in stored order with stored indices, as the daemon
passes it.

Positional resolution is reported by the resolution (`Resolution.structural`,
or a cursor-narrowed match) into the step's effect gate, rather than guessed at
compile time from the chain.

## How embedding works

`src/spec/runtime-source.ts` is the whole mechanism. It is deliberately **not** a
general TypeScript bundler.

**Reading.** `EXECUTION_MODULES` lists the shipped module names. For each,
`moduleUrl` looks for `../execution/<name>.ts` (a repository checkout) and falls
back to `../execution/source/<name>.ts` (an installed package).

**Parsing.** `parseExecutionSource` strips the Playwright type import and any
`export` modifier, records and strips sibling imports (`from './text.js'`), then
**rejects** anything else that still looks like an `import`/`export`. A module
that grows a dependency the artifact cannot carry fails the build instead of
producing a file that references a function it does not include.

**Tokens.** Each module reports its exported value names as the tokens that prove
it is used: `fn(` for a function, the bare name for a `const`.
`neededHelpers(body)` (`emit.ts:949`) iterates to a fixed point — body plus
already-chosen sources — so a helper that pulls in a module, which pulls in
another, is resolved transitively.

**Closure order.** `executionClosure(names)` returns each module once with every
dependency **ahead** of the module that imports it, and throws on a cycle.
Declaration order matters: a module may read a sibling's `const` at top level. A
chosen module's siblings ride along even when nothing in the body names them
(`emit.ts:964`).

**Shipping.** `npm run build` is `tsc -p tsconfig.json && node
scripts/copy-execution-source.mjs`. The script copies the exact `.ts` files that
`tsc` just checked into `dist/execution/source/`, which `package.json` ships via
`dist`. The artifact therefore carries typed source that was type-checked as part
of the build — not `Function.toString()` JavaScript with its types erased, and
not an emitter translation.

## The artifact contract

A generated `.flow.ts` needs **`@playwright/test` and nothing else**.

```ts
import { expect, test, type Locator, type Page } from '@playwright/test';

// This file needs @playwright/test and nothing else. A module-scoped
// declaration of the one Node global it reads keeps it type-checking in a
// project without @types/node, and shadows harmlessly in one that has it.
declare const process: { env: Record<string, string | undefined> };
```

`type Locator` is imported only when an embedded module or helper needs it. The
`process` shim exists so the file type-checks in a project with no `@types/node`;
it is a declaration, so it shadows harmlessly where the real types are present.

The file also exports `FLOW`, `flowStepIds`, `requiredInputNames`,
`requiredEnvNames`, `Vars`, `OutputKey`, `Outputs`, `createFlowRun`, `steps` and
`runFlow` — see `docs/testing-workflow.md` for integrating them into a Playwright
project.

### Regenerating existing artifacts

**A fix to a shared rule does not reach a `.flow.ts` that was generated before
it.** The source is embedded at compile time. Existing artifacts must be
recompiled:

```sh
sitelooper compile <flow-or-bundle> --out <dir>
```

The `.flow.ts` is rewritten. The user-owned `.spec.ts` beside it is left alone
unless you pass `--overwrite-spec`, so hand-written fixtures and assertions
survive a regeneration. `--allow-demoted` compiles past a demoted-pin refusal;
`--json` gives the diagnostics machine-readably.

After regenerating, run the file as a user would:

```sh
sitelooper check <name.flow.ts> --var k=v
```

## Unsupported capabilities, and how they are diagnosed

A capability the recording used and a standalone artifact cannot carry is
reported in four places at once — `unsupportedCapability`, `emit.ts:1653`:

1. a typed `Diagnostic` with code `unsupported-capability`
   (`src/spec/diagnostics.ts`), printed by every surface and carried in `--json`;
2. a `ctx.warnings` line, for callers that print warnings;
3. a `// TODO:` line, which is what `compilationBlockers` keys on to refuse the
   flow as ready;
4. a `throw` in the generated file, so a run stops there rather than skipping it.

Applied to:

- **`tabs`** — a second page needs a real handle; inventing one would re-point
  every later `page.` line at the wrong tab.
- **`read what=attr|count`** — implemented in the daemon's own tool layer; the
  artifact publishes only text and input values, so the label would be left empty
  and a consuming step would run on a blank.
- **a chain with no candidate at all** — nothing to resolve. (A position-only
  chain used to be listed here; it now resolves through the shared
  `markPoint`/`pointLocator`, exactly as the daemon resolves it.)
- **`wait_for` with a state that has no Tier 2 form** — same shape, emitted
  inline.
- **a drag with no expressible source**, and the `default` branch of the action
  switch for any tool with no Tier 2 form.

Separately, `recipe-snapshot` (a warning, not a blocker; flow-level, no step)
fires once per finding `snapshotRecipes` makes about the component store at
compile time — see `recipes.ts` above.

Also separately, `unmeasured-precondition` (a warning, not a blocker) no longer
fires at compile: a freshly compiled segment carries its fingerprint and the
artifact measures it. It fires only for a segment of a file compiled before the
vector travelled — one with the legacy `fingerprinted: true` flag and no vector
— that does not navigate itself: from the emitter
(`unmeasuredPreconditionDiagnostic`, `src/spec/ir.ts`) and from
`carryFingerprints` on repair/rerecord. Such a segment passes `'unmeasured'` to
`preconditionVerdict`, which refuses a soft url match outright; the fix is to
recompile.

A `// TODO:` with no accompanying diagnostic is the older, weaker shape — it
keeps the flow from being called ready but reaches no caller. New blockers should
use `unsupportedCapability`.

## Adding a new shared rule

1. **Put it in a self-contained module** under `src/execution/`. It may import
   Playwright types and sibling shared modules; nothing else. If it needs
   something from `compile.ts` or `shared/text.ts`, move that thing down here
   and re-export from the old location, so no existing call site changes.
2. **Export it as a function or `const`** — those are the two shapes
   `parseExecutionSource` turns into usage tokens. A module nothing names is not
   embedded.
3. **Add the module name to `EXECUTION_MODULES`** (`runtime-source.ts:15`) if it
   is new. `scripts/copy-execution-source.mjs` copies the whole directory, so it
   needs no change.
4. **Call it from the daemon**, replacing the daemon's own copy — the adapter
   should supply observations and presentation only, never reinterpret the rule.
5. **Call it from the artifact**, as an emitted helper whose body is a few lines
   around the shared call. Put the verdict's *reason strings* in the shared
   module, so both runners report failures in the same words.
6. **Test it three ways:**
   - a **unit test** of the rule itself — `test/execution-<module>.test.ts`
     (`execution-gates`, `execution-expect`, `execution-loop`,
     `execution-lifecycle`, `execution-browser` all follow this shape);
   - **`test/execution-source.test.ts`**, which strictly typechecks a generated
     artifact with the module embedded, checks each module appears exactly once,
     and checks the loader works with no repository source tree;
   - a **parity case** in `test/execution-parity.test.ts`, which runs both
     runners against a real fixture app and compares the application's mutation
     log — not merely that both reported success. Take the next cell from the
     uncovered list at the end of `PARITY_GAPS.md`.
7. **Update `PARITY_GAPS.md`**: move the entry to "Closed on this branch", citing
   the shared function and both call sites.

Two rules about the tests themselves. Do not adjust a parity expectation to make
divergent behaviour pass — the discrepancy is the finding. And when a case needs
to call an emitted helper directly, cut the WHOLE helper block out of the
generated source and rebuild every function together, as
`test/execution-parity.test.ts`, `test/execution-loop.test.ts` and
`test/execution-resolve-emit.test.ts` do. Cutting one function alone makes it
fail CLOSED the moment it gains a dependency — which reads as a passing safety
test while proving nothing.
